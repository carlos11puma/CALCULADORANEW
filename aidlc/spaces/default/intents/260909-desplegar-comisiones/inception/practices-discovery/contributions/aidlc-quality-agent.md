## Contribution

### Postura de testing heredada — sólida en Construction, no probada bajo infraestructura real

La suite existente (336/336 pruebas, cobertura 91.87%/84.64%/90.84% en `backend-api` y 95.66%/87.36%/91.61%/94.14% en `mobile-app`, ambas por encima del piso 80%/70%/80% de `team.md`) da confianza sobre la lógica de negocio en aislamiento (unit tests con mocks de `PrismaClient`, integración de endpoints vía `@nestjs/testing`). Pero **todo eso se ejecutó contra un `PrismaClient` que nunca se generó realmente**: `npx prisma generate` falló en el sandbox de Construction por bloqueo de red a `binaries.prisma.sh` (403), documentado como R-01 en `backend-api/code-generation/code-generation-plan.md` y reconfirmado en `build-and-test-summary.md` como acción pendiente "antes de cualquier build de producción". Esto significa que ninguna prueba hasta ahora ha ejercitado el cliente Prisma real contra un motor de base de datos real (Neon) — las 25 suites de `backend-api` corrieron con el cliente generado en un momento anterior o con un stub manual, y el propio `npm run build` de producción falla en ese mismo prestep. Esto no es un detalle menor de tooling: es la primera vez que este código tocará una base de datos Postgres real (Neon `main`), y el artefacto que media esa conexión (el cliente Prisma generado) **nunca ha sido validado de punta a punta**. Antes de que este intent (`260909`) cuente el despliegue como exitoso, debe haber un paso explícito que (a) ejecute `prisma generate` contra el schema real en un entorno con salida de red permitida (CI de GitHub Actions, no el sandbox), (b) corra al menos la suite de integración de `backend-api` (o un subconjunto crítico) contra el cliente generado real y una Neon `staging` real, y (c) confirme que las migraciones (`prisma migrate deploy`) aplican limpiamente sobre la rama `staging`/`main` de Neon antes de que se declare el primer despliegue a producción como aprobado. Esto es un genuine gap para la entrevista de este intent — no algo que la evidencia de `260908` ya resuelva.

### Ausencia de smoke test / health-check gate post-despliegue

Ninguno de los 4 workflows de CI (`ci-config.md`) ni el diseño de `cicd-pipeline.md` incluye un paso de verificación *después* de que Render/EAS reportan el deploy como completo. El "éxito" de un despliegue hoy se define únicamente por el exit code del proceso de build/deploy de la plataforma, no por una prueba funcional real (¿responde `/health`? ¿el login funciona? ¿una venta de prueba calcula la comisión correctamente?). `phases/operation.md` § Deployment Procedures es explícito: "Deployments to production must have a defined smoke test or health check to verify success" — este mandato de fase todavía no tiene contraparte concreta en el diseño heredado de `260908`. DEP-5 en el draft del lead ya identifica esta laguna correctamente, pero la formulo también como posición de Calidad: sin un smoke test mínimo (health-check HTTP del backend contra Neon real + un flujo E2E manual o scripted de login→venta→comisión en la app distribuida vía EAS), no hay criterio objetivo para decidir si el primer despliegue real "funcionó" o si hay que hacer rollback. Esto debe resolverse en la entrevista, no delegarse implícitamente a "Carlos lo prueba a ojo".

### El gate de aprobación manual (required reviewer) es un control de GitHub, no verificado en ejecución

El mecanismo técnico (GitHub Environment `production` con required reviewer = Carlos) está bien diseñado y confirmado ("Looks correct") en `ci-config.md`/`quality-gates.md`. Pero es importante para la entrevista distinguir diseño de verificación: nada en la evidencia de `260908` confirma que ese Environment ya existe *configurado* en el repositorio real de GitHub con Carlos efectivamente asignado como reviewer — es un diseño en papel, tal como señala `evidence.md`. Este intent (`260909`) es precisamente donde ese control pasa de diseño a artefacto real; el paso de aprovisionamiento debe incluir explícitamente "crear el Environment `production` en GitHub, asignar a Carlos como required reviewer, y confirmarlo con un dry-run" antes de que el primer despliegue a producción lo ejercite por primera vez con datos reales de comisión/salario en juego.

### Cobertura no enforced automáticamente en CI (gap ya documentado, sin agravantes nuevos para este intent)

`quality-gates.md` ya documenta que el piso de cobertura (80/70/80) se verifica manualmente en Build and Test pero no falla el build en CI (no hay `coverageThreshold`/`--coverage.thresholds` configurado). Esto no bloquea Construction y no lo elevo a bloqueante de despliegue, pero señalo que persiste como deuda técnica: si el equipo va a operar con despliegue automático a staging en cada push, un futuro cambio que erosione cobertura pasaría inadvertido hasta la próxima revisión manual. No lo convierto en pregunta nueva para la entrevista de infraestructura (está fuera de alcance de `infra`), pero recomiendo que quede registrado como acción de seguimiento post-despliegue.

### Vulnerabilidades de dependencias (T-10) — riesgo aceptado, pero relevante para el primer despliegue real

Carlos ya aceptó T-10 (vulnerabilidades de dependencias, `Not Met`) como riesgo conocido en Build and Test, con la condición explícita de que quede "como acción pendiente antes de cualquier despliegue de producción real". Esa condición ya vencida debe traerse a esta entrevista: ¿se resuelve antes de este despliegue, o se vuelve a aceptar formalmente el riesgo ahora que se trata de infraestructura real y no de un entorno de pruebas?

## Positions

AGREE: DEP-5 (verificación post-despliegue del primer arranque) — coincide exactamente con el gap de smoke-test/health-check que identifico arriba; debe resolverse en la entrevista, con un criterio mínimo concreto (health-check HTTP + flujo E2E login→venta→comisión) y un responsable de firmarlo.

AGREE: DEP-4 (rollback del primer despliegue a producción) — sin un smoke test definido (DEP-5), tampoco hay criterio objetivo para decidir cuándo ejecutar el rollback; ambas preguntas están acopladas y deberían resolverse juntas en la misma conversación de la entrevista.

AGREE: DEP-3 (gestión de secretos hacia GitHub Actions) — desde la óptica de Calidad, secretos de producción (connection string de Neon, `EXPO_TOKEN`) fuera del scope de Environment reducirían la eficacia del gate de required reviewer, porque un workflow que corre en un PR sin aprobación aún podría potencialmente acceder a secretos de producción si están a nivel de repositorio. Recomiendo que la entrevista fije explícitamente "environment secrets" para todo lo de producción.

OBJECT: el draft del lead marca "El mecanismo técnico de aprobación manual ... ya está decidido" (evidence.md, "Lo que la evidencia ya establece") como si no requiriera más atención en este intent. El *diseño* está decidido, pero no hay evidencia de que el GitHub Environment y el reviewer estén *configurados* en el repositorio real. Pido que el plan de aprovisionamiento de este intent incluya un paso explícito de verificación de esa configuración (no solo asumirla como heredada), antes de que el primer despliegue a producción dependa de ella.

AGREE (con adición): el draft no menciona explícitamente la regeneración/verificación del cliente Prisma real como pregunta de la entrevista — lo agrego como hallazgo de Calidad porque es un bloqueante funcional real (el build de producción falla hoy en ese paso) y no solo un tema de infraestructura/cuentas.
